# PRD — Tool - ScoreCheck (Agentic Coding Edition)

> Generated by the Stage 4 init script on 2026-10-24.

## 0. Agent Context Handoff

- What this system does: ScoreCheck is an open testbed for the lender's side of an alternative-data consumer credit score: it generates a synthetic Philippine behavioural panel, runs an in-house challenger in shadow mode beside a simulated black-box vendor score, and measures how the value of the model depends on who keeps the repayment outcomes. It produces a validation pack (ranking, calibration, drift, reject inference, fairness) that lets a lender or regulator see how either score behaves, plus a constrained, review-only LLM layer that drafts decline explanations from approved reason codes.
- Immutable Zones:
  - Vendor score internals: the vendor model module may only be reached through its score + three reason codes API; downstream code never reads inside it
  - Canonical behavioural-data schema (documented contract the validation layer depends on, so it can later run on other models)
  - Approved reason-code list and policy text used by the Layer 4 agent
  - checks/approved/ and MANIFEST.sha256
- Architecture map seed: Layer 1 seeded synthetic panel generator (households x 24 months, latent creditworthiness factor) -> canonical schema -> Layer 2 vendor black-box GBM behind a score API plus in-house challenger (monotonic GBM and points scorecard) in shadow mode, outcomes-ownership experiment, champion/challenger decision report -> Layer 3 validation pack / evidence kit (metrics + PDF) -> Layer 4 constrained LLM agent drafting decline explanations and credit memos, scored on a harness. Layers 2-3 run end to end from one command.
- Scope constraints:
  - Consumer borrowers only (thin-file individuals and households); no MSME or firm-level scoring
  - Synthetic data plus one public dataset only; no CreditBPO code, data, clients or methods beyond published general practice
  - No Kayana, Maya or Trusting Social data or internals; the vendor score is a simulated black box and they are never named as partners or users
  - Never claim the in-house model beats any real vendor; the write-up claims a decision method, not a verdict on a named company
  - The Layer 4 agent may only use approved reason codes and policy text, must never invent a figure or reason, and is review-only (a human signs every decline)
  - Governance mappings (EU AI Act, RA 10173, RA 9510, BSP circulars) must be checked against source text, never written from memory
- Task complexity tier: Complex

## 1. Product Overview

- Problem statement: A data owner that rents a credit model built on its own behavioural data cannot measure what the vendor's black-box score is worth or what it would take to own one.
- Core user story: As a data owner or lender buying an alternative-data credit score, I want to validate the vendor's black-box score against an in-house challenger on my own data so I can decide with evidence when to keep, renegotiate or replace the vendor.
- Success criteria:
  - Public repo from the first commit, with Layer 1 generator and canonical schema
  - Layers 2 and 3 run end to end from one command
  - README a credit analyst can run in ten minutes, with a limitations section
  - Layer 4 harness with a results table (faithfulness to reason codes, reading level, policy compliance, cost and latency per decision)
  - Validation pack PDF generated from the evidence kit, plus a model risk note with governance mapping checked against sources
  - One public dataset run whose licence allows public redistribution of results (check Home Credit Default Risk and Give Me Some Credit terms first)

## 2. Core Features & Acceptance Criteria

MVP Features
- [ ] Feature: Synthetic behavioural panel — Given a seed and generator config, When the panel generator runs, Then it writes about 200,000 households over 24 months of electricity, mobile and e-wallet records in the canonical schema, driven by one latent creditworthiness factor with known default labels and Philippine data quirks (shared accounts, multiple SIMs, mostly prepaid, remittance spikes), and the same seed reproduces identical output
- [ ] Feature: Black-box vendor score API — Given a vendor gradient-boosted model trained on the panel, When downstream code requests a score for an applicant, Then it receives only a score and three reason codes, with no access to the model's internals
- [ ] Feature: In-house challenger in shadow mode — Given the same applicants scored by the vendor, When the monotonic-constrained GBM and the points scorecard score them using only the data owner's features, Then both challenger scores are recorded beside the vendor score without changing any decision
- [ ] Feature: Outcomes-ownership experiment — Given two regimes over 24 simulated months, one where repayment outcomes flow only to the vendor and one where the data owner keeps them too, When the experiment runs, Then it produces learning curves showing how the vendor-versus-challenger gap moves in each regime
- [ ] Feature: Champion and challenger decision report — Given vendor and challenger scores with outcomes, When the report is generated, Then it shows by segment and by length of behavioural history (thin-file versus thick-file) where the vendor still adds lift, where the challenger has caught up, and what a phased switch would cost in approval rate and expected loss
- [ ] Feature: Lender validation pack — Given scores and outcomes for both models, including a simulated year-two shift (new lender channel, El Nino shock to rural incomes, telco pricing change), When the evidence kit runs, Then it reports ranking performance overall and by segment, calibration by segment, PSI and characteristic-level drift, reject inference, fairness checks with a proxy-risk note, and approval and loss trade-off curves at several cut-offs, and renders them as a PDF
- [ ] Feature: Constrained decline-explanation agent — Given a score, its reason codes and the policy rules, When the agent drafts a borrower-facing decline explanation and a short credit memo, Then the output uses only approved reason codes and policy text, invents no figures or reasons, is marked for human sign-off, and is scored on the harness for faithfulness, reading level, policy compliance, cost and latency

## 3. Architecture, Stack & Interface Contracts

- Tech stack: Python 3 with pandas and numpy for the panel, scikit-learn plus a GBM library with monotonic constraints (TODO confirm LightGBM or XGBoost) for vendor and challenger, a points-scorecard implementation, an LLM API for Layer 4, and a PDF report generator (TODO confirm)
- Data flow: Seeded generator -> panel in canonical schema -> vendor model (behind score API) and challenger models score the same applicants -> outcomes fed back per regime over 24 months -> evidence kit computes metrics and renders validation pack PDF -> Layer 4 agent reads score + reason codes + policy text and drafts explanation for human review
- Integration points: Vendor score API (score + three reason codes only); LLM API for Layer 4; one public credit dataset (Home Credit Default Risk or Give Me Some Credit, licence to be checked)
- Interface / schema contracts: Documented canonical behavioural-data schema; vendor score API returns exactly a score and three reason codes; approved reason-code list and policy text for the agent; generator output is deterministic for a given seed
