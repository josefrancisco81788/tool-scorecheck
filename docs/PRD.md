# PRD — Tool - ScoreCheck (Agentic Coding Edition)

> Generated by the Stage 4 init script on 2026-10-24.

## 0. Agent Context Handoff

- What this system does: ScoreCheck is an open testbed for the lender's side of an alternative-data consumer credit score: it generates a synthetic Philippine behavioural panel, runs an in-house challenger in shadow mode beside a simulated black-box vendor score, and measures how the value of the model depends on who keeps the repayment outcomes. It produces a validation pack (ranking, calibration, drift, reject inference, fairness) that lets a lender or regulator see how either score behaves, plus a constrained, review-only LLM layer that drafts decline explanations from approved reason codes.
- Immutable Zones:
  - Vendor score internals: the vendor model module may only be reached through its score + three reason codes API (full-book `vendor.score`, or the Feature 004 regime reader); downstream code never reads inside it
  - Behavioural-data schema (documented, with a fixed seed so every result can be reproduced)
  - Approved reason-code list and policy text used by the Layer 4 agent
  - checks/approved/ and MANIFEST.sha256
- Architecture map seed: Layer 1 seeded synthetic panel generator (default 50,000 households over 24 months, full run about 200,000, driven by ability, willingness, shocks, and a vendor-only signal) -> documented schema -> Layer 2 vendor score API plus in-house challengers (LightGBM, XGBoost, and histogram gradient boosting, each unconstrained and, where supported, with a monotone refit, plus a points scorecard) in shadow mode, outcomes-ownership experiment, champion/challenger decision report -> Layer 3 validation pack (metrics + PDF) -> Layer 4 constrained LLM agent drafting decline explanations and credit memos, scored on a harness. Layers 2-3 run end to end from one command.
- Scope constraints:
  - Consumer borrowers only (thin-file individuals and households); no MSME or firm-level scoring
  - Synthetic data plus one public dataset only; no CreditBPO code, data, clients or methods beyond published general practice
  - No Kayana, Maya or Trusting Social data or internals; the vendor score is a simulated black box and they are never named as partners or users
  - Never claim the in-house model beats any real vendor; the write-up claims a decision method, not a verdict on a named company
  - The Layer 4 agent may only use approved reason codes and policy text, must never invent a figure or reason, and is review-only (a human signs every decline)
  - Governance mappings (EU AI Act, RA 10173, RA 9510, BSP circulars) must be checked against source text, never written from memory
- Task complexity tier: Complex

## 1. Product Overview

- Problem statement: A data owner that rents a credit model built on its own behavioural data cannot measure what the vendor's black-box score is worth or what it would take to own one.
- Core user story: As a data owner or lender buying an alternative-data credit score, I want to validate the vendor's black-box score against an in-house challenger on my own data so I can decide with evidence when to keep, renegotiate or replace the vendor.
- Success criteria:
  - Public repo from the first commit, with Layer 1 generator and documented schema
  - Layers 2 and 3 run end to end from one command
  - README a credit analyst can run in ten minutes, with a limitations section. The default command is the 50,000-household panel plus UCI Default of Credit Card Clients (id 350). The README states that Home Credit and 200,000 households are the full command.
  - Layer 4 harness with a results table (faithfulness to reason codes, reading level, policy compliance, cost and latency per decision)
  - Validation pack PDF generated by the repo, plus a model risk note with governance mapping checked against sources
  - One public dataset run on Home Credit Default Risk in the full command, and on UCI Default of Credit Card Clients in the default command. Give Me Some Credit is not used. Licence was set aside by decision on 2026-10-25. The choice is grain and quality.

## 2. Core Features & Acceptance Criteria

MVP Features
- [x] Feature: Synthetic behavioural panel — Given a seed and generator config, When the panel generator runs, Then the default run writes 50,000 households over 24 months and the full run writes about 200,000. The command banner, the README, and the report header state which scale ran. Behaviour and default are driven by ability, willingness, shocks, and a vendor-only signal. Ground truth stays apart from the model columns. The output conforms to `application_features`, includes the Philippine quirks (shared accounts, multiple SIMs, mostly prepaid, remittance spikes), and the same seed reproduces the same logical table.
- [ ] Feature: Black-box vendor score API — Given a vendor gradient-boosted model trained on the panel, When downstream code requests a score for an applicant, Then it receives only a score and three reason codes, with no access to the model's internals
- [ ] Feature: In-house challenger in shadow mode — Given the same applicants scored by the vendor, When LightGBM, XGBoost, and histogram gradient boosting each fit unconstrained and, where the library supports it, with a monotone refit, plus the points scorecard, score them using only the data owner's features, Then all four lines are recorded beside the vendor score without changing any decision
- [ ] Feature: Outcomes-ownership experiment — Given two regimes over 24 simulated months, one where repayment outcomes flow only to the vendor and one where the data owner keeps them too, When the experiment runs, Then it produces learning curves showing how the vendor-versus-challenger gap moves in each regime. Hidden outcomes live in `data/experiment/<run id>/outcomes.parquet`; `application_features` stays the Feature 001 snapshot. A vendor refit is a writer inside `vendor/` that writes a regime ledger under `data/experiment/<run id>/<regime>/`, not another `vendor.publish`. The hypothesis is recorded in the report and is not a target the generator is adjusted to hit.
- [ ] Feature: Champion and challenger decision report — Given vendor and challenger scores with outcomes, When the report is generated, Then it shows by segment and by length of behavioural history (thin-file versus thick-file) where the vendor still adds lift, where the challenger has caught up, and what a phased switch would cost in approval rate and expected loss
- [ ] Feature: Lender validation pack — Given scores and outcomes for both models, including a simulated year-two shift (new lender channel, El Nino shock to rural incomes, telco pricing change), When the validation pack is generated, Then it reports ranking performance overall and by segment, calibration by segment, PSI and characteristic-level drift, reject inference, fairness checks with a proxy-risk note, and approval and loss trade-off curves at several cut-offs, and renders them as a PDF. The default command scores UCI Default of Credit Card Clients (id 350) on its own frame. The full command scores Home Credit aggregates on their own frame. Give Me Some Credit is not used.
- [ ] Feature: Constrained decline-explanation agent — Given a score, its reason codes and the policy rules, When the agent drafts a borrower-facing decline explanation and a short credit memo, Then the output uses only approved reason codes and policy text, invents no figures or reasons, is marked for human sign-off, and is scored on the harness for faithfulness, reading level, policy compliance, cost and latency

## 3. Architecture, Stack & Interface Contracts

- Tech stack: Python 3 with pandas and numpy for the panel. LightGBM, XGBoost, and scikit-learn `HistGradientBoostingClassifier`, each unconstrained and, where supported, with a monotone refit, plus an in-house weight-of-evidence scorecard. An LLM API for Layer 4. ReportLab for the validation-pack PDF.
- Data flow: Seeded generator -> panel in the documented schema -> vendor model (behind score API) and challenger models score the same applicants -> outcomes fed back per regime over 24 months -> validation code computes metrics and renders the validation pack PDF -> Layer 4 agent reads score + reason codes + policy text and drafts explanation for human review
- Integration points: Vendor score API (a score and three reason codes only). LLM API for Layer 4. Home Credit Default Risk on the full command, and UCI Default of Credit Card Clients (id 350) on the default command. Give Me Some Credit is not used.
- Interface / schema contracts: Documented behavioural-data schema; vendor score API returns exactly a score and three reason codes; approved reason-code list and policy text for the agent; generator output is deterministic for a given seed
